# Пользовательские сайты для поиска вакансий

Статус: спецификация для реализации. Дата: 2026-09-19.

## 1. Задача

Пользователь управляет личным списком сайтов в разделе «Сайты для поиска»: добавляет, редактирует и удаляет сайты, задаёт URL, параметры поиска, пагинацию и JavaScript для извлечения данных. Новый сайт начинает участвовать в следующем запуске парсинга без добавления Python-класса и без перезапуска приложения.

Конфигурации хранятся в таблице `parsers`. Вместо отдельных реализаций HH и GeekJob используется один `ConfiguredVacancyParser`, совместимый с `GeneralVacancyParser`. Настройки загружаются один раз при старте операции, могут кешироваться в Redis и не меняются внутри уже созданного задания.

Документ описывает будущую реализацию. Создание этой спецификации не изменяет работу приложения.

## 2. Продуктовые решения

Личный характер списков подтверждён пользователем; остальные уточнения ниже — предлагаемые правила реализации там, где исходный запрос не задаёт деталей.

1. **Подтверждено пользователем:** сайты личные. Каждый пользователь получает собственные редактируемые HH и GeekJob; изменения не затрагивают других пользователей.
2. В каждом новом автопарсинге участвуют все сайты пользователя, существующие на момент создания задания. Выбор подмножества и отдельный переключатель активности в первую версию не входят.
3. Создание и редактирование открываются на отдельных страницах. После успешного сохранения происходит переход к списку с инвалидацией его кеша.
4. Список имеет серверную пагинацию и фиксированный порядок `created_at DESC, id DESC`. Редактирование не меняет `created_at` и позицию записи.
5. Редактирование разрешено во время парсинга. Новые значения применяются к следующим заданиям; текущие используют сохранённый снимок конфигурации.
6. Удаление запрещено, пока сайт используется заданием со статусом `pending` или `running`. Ожидание в очереди также считается использованием. После завершения парсинга именно этого сайта удаление разрешено, даже если другие сайты или генерация писем ещё работают.
7. Удаление сайта сохраняет историю заданий, найденные вакансии и письма. Начальные HH и GeekJob удаляются по тем же правилам, что остальные сайты.
8. Если список сайтов пуст, запуск возвращает понятную ошибку и ссылку на раздел сайтов; пустое задание в БД не создаётся.

Особенности, которые нужно учесть:

- `GeneralVacancyParser.__init__` сейчас игнорирует переданное название и записывает в `_name` домен `base_url`. Название, домен и ID необходимо разделить.
- `format_url` сейчас различается главным образом именем параметра запроса: `text` у HH, `qs` у GeekJob.
- Пагинация сейчас перебирает `range(pages)` и ограничивается `HH_MAX_PAGES`. Для новых сайтов нужен настраиваемый первый номер страницы и общий лимит.
- `evaluate_pagination` возвращает видимые номера страниц, а не обязательно значения query-параметра. У HH видимые номера начинаются с 1, а параметр `page` — с 0.
- Метод без пагинации уже вызывает общую прокрутку страницы перед извлечением карточек; этот сценарий нужно сохранить.
- Помимо `VacancyScrapingService`, имеются прямые вызовы HH-специфичного `parse_hh` в endpoint `/parse` и сервисе писем. Пользовательские пути разбора URL должны использовать единый сервис, иначе добавленный сайт будет поддерживаться не во всех формах.

## 4. Модель данных

### 4.1. Таблица `parsers`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | integer, PK | Стабильный идентификатор конфигурации |
| `user_id` | integer, FK `users.id`, NOT NULL | Владелец; определяется из авторизации |
| `name` | varchar(255), NOT NULL | Название в интерфейсе, например «HeadHunter» |
| `site_key` | varchar(255), NOT NULL | Нормализованный hostname для поиска парсера по URL |
| `base_url` | text, NOT NULL | Адрес списка/поиска вакансий |
| `single_url` | text, NOT NULL | Шаблон страницы вакансии с `{vacancy_id}` |
| `has_pagination` | boolean, NOT NULL | Нужен ли обход нескольких страниц |
| `evaluate_vacancy_list` | text, NOT NULL | JS-функция извлечения карточек |
| `evaluate_vacancy_page` | text, NOT NULL | JS-функция извлечения одной вакансии |
| `evaluate_pagination` | text, nullable | JS-функция получения видимых номеров страниц |
| `format_url` | jsonb, NOT NULL | Декларативные правила формирования URL поиска |
| `pagination_start` | integer, NOT NULL, default 0 | Значение параметра для первой страницы |
| `max_pages` | integer, NOT NULL, default 5 | Максимальное число загружаемых страниц |
| `version` | integer, NOT NULL, default 1 | Версия записи, увеличивается при редактировании |
| `created_at` | timestamp UTC, NOT NULL | Дата создания |
| `updated_at` | timestamp UTC, NOT NULL | Дата последнего изменения |

Каноническое имя поля — `evaluate_vacancy_list`, как у метода. Варианты `evaulate_list` и `evaluate_list` не вводятся.

Ограничения и индексы:

- `UNIQUE(user_id, site_key)`: одна конфигурация на hostname у пользователя, без неоднозначного выбора парсера по URL. Другой пользователь может добавить тот же hostname.
- Индекс `(user_id, created_at DESC, id DESC)` для списка.
- `site_key` вычисляет backend из `base_url`: hostname в нижнем регистре, с одинаковой нормализацией при сохранении и поиске. Не использовать сравнение через `endswith`; `www` и другие поддомены не объединять неявно.
- `pagination_start >= 0`, `1 <= max_pages <= 50`. Значение 50 — предлагаемый серверный предел первой версии.
- При `has_pagination=true` обязательны `evaluate_pagination` и настройка page-параметра в `format_url`; при `false` скрипт пагинации не исполняется.
- `created_at` задаёт сервер и не принимает в CRUD; `updated_at` и `version` меняются только при успешном сохранении.

### 4.2. Снимок в `parsing_site_jobs`

Добавить:

- `parser_id`: nullable FK на `parsers.id`, `ON DELETE SET NULL`.
- `parser_version`: версия конфигурации при запуске.
- `parser_snapshot`: JSONB со всеми настройками для восстановления парсера, включая `id`, `user_id`, `name`, `site_key`, `version` и `schema_version=1`.

Существующий `site_key` остаётся историческим значением на момент запуска. Переименование сайта или изменение домена не переписывает задания и `AutoParsedJob.web_site`. Существующее ограничение `(parsing_job_id, site_key)` совместимо с уникальным доменом в личном каталоге.

Для новых заданий снимок обязателен; исторические завершённые задания могут иметь пустые новые поля. Индекс `(parser_id, status)` нужен для проверки удаления. Нельзя каскадно удалять задания вместе с конфигурацией.

### 4.3. Ревизия каталога

Добавить `users.parsers_revision`: bigint, NOT NULL, default 0. Увеличивать в той же транзакции, что создание, изменение или удаление парсера. Это версия всего личного каталога для кеша; `parsers.version` — версия одной записи.

## 5. Контракт конфигурации

### 5.1. JS-функции `evaluate_*`

Хранятся строки JS-функций без аргументов, которые исполняются через `page.evaluate` в странице соответствующего сайта, как сейчас. Backend не исполняет пользовательский Python и не использует Python `eval`/`exec`.

Список вакансий:

```javascript
() => [...document.querySelectorAll('.vacancy')].map(card => ({
  title: card.querySelector('a').textContent.trim(),
  vacancy_id: card.dataset.id,
  link: card.querySelector('a').href
}))
```

Результат: массив объектов `{title: string, vacancy_id: string, link: string}`. Все три поля непустые, `link` — абсолютный HTTP(S) URL. ID может быть нечисловым, как у GeekJob. Повторения одного `vacancy_id` в рамках сайта отфильтровываются существующим алгоритмом.

Страница вакансии:

```javascript
() => ({
  job_title: document.querySelector('h1')?.textContent?.trim() || '',
  job_text: document.querySelector('article')?.textContent?.trim() || ''
})
```

Результат: `{job_title: string, job_text: string, job_url?: string}`. Пустой `job_text` считается ошибкой извлечения. Фактически открытый URL задаёт backend; необязательный `job_url` из JS не подменяет его.

Пагинация:

```javascript
() => [...document.querySelectorAll('.pagination a')]
  .map(item => item.textContent.trim())
```

Результат: массив видимых номеров страниц типа string или integer, с нумерацией от 1. Backend отбрасывает нечисловые, нецелые и неположительные значения. Пустой массив или отсутствие подходящих номеров означает одну страницу. Иначе `page_count = min(max(valid_numbers), max_pages)`.

Значения page-параметра: `pagination_start + i` для `i` от 0 до `page_count - 1`. При `has_pagination=false` выполняется один проход с существующей прокруткой; настройки пагинации игнорируются. Cursor-пагинация, POST-поиск, авторизация на сайтах и сценарии нажатия «Следующая страница» в первую версию не входят.

Неверный тип результата — ошибка конфигурации с указанием сайта и поля. Ошибка списка/пагинации завершает задание этого сайта как `failed`; ошибка отдельной вакансии учитывается существующим механизмом `failed_count`. Ошибки одного сайта не останавливают остальные.

### 5.2. `single_url` и `format_url`

`single_url` содержит обязательный плейсхолдер `{vacancy_id}`, например `https://hh.ru/vacancy/{vacancy_id}`. ID кодируется как компонент URL, чтобы `/`, `?`, `#` внутри ID не меняли структуру адреса. Шаблон не допускает произвольных выражений или неизвестных плейсхолдеров.

`format_url` — JSON-конфигурация, которую UI редактирует обычными полями и списком query-параметров:

```json
{
  "url_template": "{base_url}",
  "query_params": {
    "text": "{text}",
    "page": "{page}",
    "only_with_salary": "true"
  }
}
```

- `url_template` поддерживает `{base_url}`, `{text}`, `{page}`; query-параметры задаются отдельно. Текст и номер страницы можно использовать в пути, например `https://jobs.example/search/{text}`. Динамический hostname не поддерживается.
- `query_params` — объект с уникальными непустыми ключами и строковыми значениями. Значение может быть константой либо содержать `{text}`/`{page}`; неизвестные плейсхолдеры дают `422`.
- `{text}` — поисковый запрос; `{page}` — рассчитанный номер страницы. При отсутствии аргумента `page` query-параметр с `{page}` целиком пропускается. Если `{page}` находится в пути, для первого запроса используется `pagination_start`.
- Query-параметры исходного URL сохраняются; явно заданные ключи из `query_params` их заменяют. Query строится URL-библиотекой, без ручной конкатенации `?` и `&` и без двойного кодирования. Значения для пути кодируются отдельно как сегменты пути.
- Для включённой пагинации `{page}` должен присутствовать в query или пути. Для выключенной пагинации аргумент `page` не передаётся.
- Метод Python `format_url(url, **kwargs)` реализует эти правила. Произвольный код для построения URL не нужен для текущих HH/GeekJob и не входит в первую версию; пользовательский JS доступен в трёх `evaluate_*`.
- `site_key`, hostname `single_url` и hostname поискового URL должны совпадать. Поддержка нескольких доменов у одного парсера — отдельное расширение.

### 5.3. Валидация и исполнение

При сохранении проверять обязательные поля, длины, URL, шаблоны и структуру `format_url`; JS хранить как исходный текст с ограничением размера, например 64 KiB на поле. Сохранение не открывает сайт и не обещает, что селекторы подходят текущей странице. Синтаксические и runtime-ошибки JS отображаются при выполнении с названием соответствующего поля.

Поскольку пользователь задаёт и URL, и исполняемый JS, использовать отдельный browser context без сессии приложения и bindings к backend. Разрешать HTTP(S); блокировать доступ к loopback, private/link-local адресам и внутренним сервисам на уровне исходящих запросов браузера, включая редиректы, ресурсы и запросы JS. Проверки одного исходного URL недостаточно.

Предусмотреть жёсткий лимит времени исполнения JS с закрытием/завершением зависшего браузерного процесса: один timeout ожидания результата не останавливает бесконечный цикл в JS. Лимиты времени, размера результата и количества карточек задаются сервером. Эти ограничения не являются пользовательскими настройками парсера.

## 6. Загрузка и жизненный цикл парсеров

### 6.1. Общий адаптер

`ConfiguredVacancyParser(GeneralVacancyParser)` принимает валидированный неизменяемый DTO конфигурации:

| Метод | Источник поведения |
| --- | --- |
| `get_name()` | `name` |
| `get_site_key()` | `site_key`, отдельный метод для технического домена |
| `get_single_url(vacancy_id)` | `single_url` |
| `evaluate_vacancy_list()` | `evaluate_vacancy_list` |
| `evaluate_vacancy_page()` | `evaluate_vacancy_page` |
| `evaluate_pagination()` | `evaluate_pagination` |
| `format_url(url, **kwargs)` | `format_url`, `pagination_start` |

Карта `_parser_map` индексируется по `get_site_key()`, а не по пользовательскому названию. Общий обход остаётся в `GeneralVacancyParser`; замена сайта не требует нового класса.

### 6.2. Автопарсинг и Celery

Точка фиксации настроек — успешное создание задания в `/auto-parse/start`, до помещения задач в очередь:

1. В короткой транзакции заблокировать строку владельца каталога и прочитать его `parsers_revision`.
2. Один раз получить полный каталог этой ревизии через `ParserCatalogService`, из Redis либо БД. UI-пагинация не ограничивает список парсеров для запуска.
3. При пустом каталоге вернуть `409 parsers_empty`. Иначе создать `ParsingJob` и все `ParsingSiteJob` со снимками в этой же транзакции.
4. После commit поставить по одной задаче на сохранённое задание сайта. Рекомендуемый аргумент Celery — `parsing_site_job_id`; владельца, query и снимок читать из БД.
5. Воркер выполняет существующий атомарный claim, создаёт один `ConfiguredVacancyParser` из сохранённого снимка и передаёт его в `SiteParseService`.
6. Повторная доставка задачи не создаёт повторную работу; повтор выполнения того же задания использует тот же снимок. Новый пользовательский запуск получает актуальный каталог.

Запрещено повторно читать текущую конфигурацию `parsers` для каждой вакансии, страницы или попытки Celery. Чтение сохранённого снимка задания воркером не является повторной загрузкой каталога. Сбой отправки в очередь обрабатывается существующим `fail_pending_dispatch`, чтобы незапущенные задания освобождали запрет удаления.

Текущее поведение `generation_mode`, генерации писем и событий прогресса сохраняется.

### 6.3. `VacancyScrapingService`

Убрать обращение к статическому реестру из `__init__`. Инициализацию сделать явно асинхронной, например фабрикой `await VacancyScrapingService.for_user(user_id, catalog_service)` либо `from_snapshot(...)` для уже созданного задания.

- `_parsers: list[GeneralVacancyParser]` и `_parser_map` формируются один раз на операцию из DTO каталога/снимка.
- Не хранить изменяемый сервис с каталогом одного пользователя как общий singleton для разных запросов.
- `run_parse_job`, если сохраняется как поддерживаемый путь, использует те же сохранённые задания сайтов и правила занятости, а не второй независимый способ запуска.
- `parse_single` получает контекст пользователя; использует его парсер по hostname. Для неизвестного сайта сохраняется общий разбор текста страницы.
- Внедрение в сервис писем и endpoint `/parse` должно передавать `user_id` и использовать этот путь вместо прямого HH-only разбора.
- Кеш извлечённого текста по одному URL тоже необходимо разделить по пользователю и ревизии каталога: например `vacancy-text:v1:{user_id}:{revision}:{url_hash}`. Тогда изменение/удаление парсера не оставит старый результат для нового запуска.

### 6.4. Запрет удаления и конкурентные операции

CRUD, создание задания и регистрация одиночного разбора блокируют одну и ту же строку пользователя в БД. Проверка занятости и удаление выполняются в одной транзакции. Это сериализует старт и удаление: если старт прошёл первым, удаление получит `409`; если удаление первым — следующий запуск не увидит сайт. Не держать эту блокировку во время браузерной работы.

Автопарсинг удерживает занятость через `ParsingSiteJob.parser_id` со статусом `pending/running`. Проверяется конкретный парсер, а не статус родительского задания и не текущий домен, который пользователь может изменить.

Для одиночного разбора зарегистрированным парсером нужна аналогичная запись использования без создания фиктивного задания автопоиска: небольшая таблица `parser_usages` с `id`, `parser_id`, `user_id`, `started_at`, `expires_at`. Для `parser_id` задать FK `ON DELETE CASCADE` и индекс `(parser_id, expires_at)`: это временные записи, а не история. Запись создаётся атомарно с фиксацией конфигурации и удаляется в `finally`. Срок действия должен покрывать серверный жёсткий deadline операции; по достижении deadline браузер принудительно останавливается. Удаление учитывает неистёкшие записи использования. Кешированный ответ без браузерной работы такую запись не создаёт.

При аварии воркера статус `running` не должен оставаться навечно. Обработка ошибки/жёсткого таймаута и восстановление зависших задач переводят запись в `failed` только после прекращения её исполнения. Запрет удаления не снимается простым истечением Redis TTL, пока сайт ещё парсится.

Ответ отказа: `409` с `detail.code = "parser_in_use"` и сообщением «Сайт сейчас используется для парсинга. Удаление станет доступно после завершения». Поле `can_delete` в списке информационное; backend всегда повторяет проверку в транзакции.

## 7. Кеш каталога и инвалидация

`ParserCatalogService` читает конфигурации через repository и опциональный Redis cache. Кеш содержит JSON DTO, а не ORM-объекты, Python-классы или браузерные страницы.

- Ключ: `parsers:v1:{user_id}:{parsers_revision}`, TTL, например, 1 час.
- Перед получением каталога на старте операции читать ревизию из БД. Чтение одного числа допускается даже при cache hit: полные конфигурации всё равно загружаются один раз, а свежесть не зависит от Redis.
- Cache miss: прочитать все конфигурации пользователя, валидировать DTO и записать каталог под этой ревизией. Пустой каталог тоже является валидным кешируемым значением.
- Create/update/delete и начальное заполнение меняют каталог и увеличивают ревизию атомарно. После commit удалить старый ключ по возможности; это очистка, а не единственная гарантия свежести.
- Новая операция после commit использует новый ключ. Запоздалая запись старого кеша безопасна: она попадёт под старую ревизию, которую новые операции больше не выбирают.
- При недоступном Redis читать БД; не отменять уже сохранённое изменение из-за ошибки удаления кеша. Повреждённый payload считается cache miss.
- У Redis задать короткий timeout, чтобы его недоступность не удерживала транзакционную блокировку каталога надолго.
- При выключенном кеше использовать тот же сервис и прямое чтение БД. Локальный бессрочный `lru_cache` каталога не вводить.
- Уже сохранённые снимки заданий не инвалидируются.
- Состояния `is_in_use`/`can_delete` вычисляются из БД отдельно и не входят в долговременный кеш конфигураций.

Одна ревизия и общий Redis обеспечивают одинаковое поведение API-процессов и Celery без обязательного Pub/Sub для инвалидации.

## 8. API

Подключить router `/parsers` к существующему API v1. Все операции требуют авторизации; `user_id` берётся только из `CurrentUser`. Чужой ID возвращает `404`, включая попытки изменения и удаления.

| Метод и путь относительно API v1 | Результат |
| --- | --- |
| `GET /parsers?page=1&page_size=20` | `{items, total, page, page_size}`; `page >= 1`, `1 <= page_size <= 100`, порядок `created_at DESC, id DESC` |
| `GET /parsers/{id}` | Полная конфигурация для редактирования |
| `POST /parsers` | `201`, созданная конфигурация |
| `PUT /parsers/{id}` | `200`, полная сохранённая конфигурация; запрос содержит ожидаемую `version` |
| `DELETE /parsers/{id}` | `204` либо `409 parser_in_use` |

Элемент списка: `id`, `name`, `site_key`, `base_url`, `has_pagination`, `version`, `created_at`, `updated_at`, `is_in_use`, `can_delete`. JS и полную конфигурацию возвращает detail endpoint, а не каждая строка списка.

Тело создания: все редактируемые поля из раздела 4.1, кроме вычисляемых и служебных (`id`, `user_id`, `site_key`, версий и дат). PUT содержит те же поля и ожидаемую `version`. Ошибка версии — `409 parser_version_conflict`; форма сохраняет введённый текст и предлагает загрузить актуальную запись. Дублирующий домен — `409 parser_domain_exists`; неверные поля — `422` с привязкой к полю.

Пагинация offset-based: записи могут сдвигаться между страницами при конкурентном добавлении; стабильный снимок всего списка между HTTP-запросами не требуется. Размер и счётчик списка относятся только к текущему пользователю.

## 9. Frontend

### 9.1. Маршруты и список

- `/search-sites` — страница «Сайты для поиска».
- `/search-sites/new` — создание.
- `/search-sites/:id/edit` — редактирование.

Маршруты используют существующие `PrivateRoute` и `AppShell`; в Sidebar добавить отдельный пункт. Route-level страницы разместить в `pages/`, API/типы/хуки/форму — в `features/search-sites/`.

В списке показывать название, домен/URL, пагинацию, дату создания, состояние «Используется для парсинга» и действия «Редактировать»/«Удалить». Кнопка «Добавить сайт» открывает отдельную страницу. Страница и размер списка сохраняются в query string.

Удаление запрашивает подтверждение с названием сайта. Для занятого сайта кнопка отключена с пояснением. Если состояние изменилось после загрузки списка, обработать `409`, обновить список и показать сообщение сервера. Обновлять занятость при возвращении фокуса, после запуска/завершения парсинга и периодически, например раз в 5 секунд, пока страница списка открыта.

Предусмотреть loading/error/empty состояния. После удаления последнего элемента страницы перейти на предыдущую непустую страницу. В пустом списке показать действие «Добавить сайт»; HH/GeekJob автоматически обратно не восстанавливать.

### 9.2. Форма

Поля сгруппированы по назначению:

- Основное: название, `base_url`, `single_url` с подсказкой `{vacancy_id}`.
- Поиск: URL-шаблон, редактируемые строки query-параметров; подсказки `{text}` и `{page}`.
- Пагинация: переключатель, первый номер страницы, максимум страниц, JS `evaluate_pagination`.
- Извлечение: отдельные многострочные редакторы `evaluate_vacancy_list` и `evaluate_vacancy_page`, примеры ожидаемого результата.

При выключенной пагинации её поля скрыты/отключены, обязательность снята. Можно сохранять введённый JS для последующего включения, но backend его не исполняет.

Есть кнопки «Сохранить» и «Отмена». Во время запроса повторное сохранение отключено. Ошибка остаётся на странице с сохранением значений и подсветкой полей. При редактировании занятого сайта показать: «Изменения применятся к следующим запускам. Текущий парсинг использует прежние настройки».

### 9.3. Кеш интерфейса и переходы

Использовать существующий TanStack Query:

- список: `['parsers', userId, 'list', page, pageSize]`;
- detail: `['parsers', userId, 'detail', parserId]`.

После успешного создания инвалидировать все страницы списка пользователя и перейти на первую страницу — новая запись находится сверху. После редактирования обновить/инвалидировать detail и все страницы списка, затем вернуться на исходную страницу списка; при прямом открытии формы — на первую. После удаления удалить detail из кеша и инвалидировать все страницы списка. Инвалидация должна гарантировать refetch при открытии списка, включая ранее неактивные queries.

При ошибке сохранения перехода нет. «Отмена» возвращает к списку без изменения данных. Кеш должен очищаться при выходе/смене пользователя. Все строки добавить в `ru.json` и `en.json`.

В форме автопарсинга убрать утверждения о фиксированном наборе HH/GeekJob, если они есть. При `parsers_empty` показать сообщение и ссылку на «Сайты для поиска».

## 10. Миграции и начальные данные

Создать Alembic-миграцию на актуальном head с учётом уже имеющихся миграций режимов генерации: `parsers`, ревизия каталога, поля снимка/ссылки в `parsing_site_jobs`, `parser_usages` и индексы.

Для каждого существующего пользователя создать личные записи:

| Настройка | HH | GeekJob |
| --- | --- | --- |
| `name` | `hh.ru` | `geekjob.ru` |
| `site_key` | `hh.ru` | `geekjob.ru` |
| `base_url` | `https://hh.ru/search/vacancy` | `https://geekjob.ru/vacancies` |
| `single_url` | `https://hh.ru/vacancy/{vacancy_id}` | `https://geekjob.ru/vacancy/{vacancy_id}` |
| `has_pagination` | `true` | `false` |
| `format_url.url_template` | `{base_url}` | `{base_url}` |
| `format_url.query_params` | `{"text":"{text}","page":"{page}"}` | `{"qs":"{text}","page":"{page}"}` |
| `pagination_start` | `0` | `0` |
| `max_pages` | `5` | `5`, не используется при выключенной пагинации |
| `evaluate_vacancy_list` | Точная строка из `HHVacancyParser` | Точная строка из `GeekJobVacancyParser` |
| `evaluate_vacancy_page` | Точная строка из `HHVacancyParser` | Точная строка из `GeekJobVacancyParser` |
| `evaluate_pagination` | Точная строка из `HHVacancyParser` | Точная строка из `GeekJobVacancyParser`, не исполняется |

JS фиксируется в миграции как данные, без импорта меняющихся runtime-классов. Runtime-шаблоны начальных данных используются при регистрации нового пользователя. Создание пользователя и двух парсеров выполняется атомарно. Повторное выполнение seed не перезаписывает пользовательские настройки; seed не запускается при каждом чтении каталога, чтобы не восстанавливать удалённые сайты.

Если в текущем окружении переопределён `HH_MAX_PAGES`, перенос этого значения в начальную конфигурацию HH должен быть явным шагом развёртывания; миграция не читает окружение для изменения исторического результата.

Переход выполнять с остановкой приёма новых заданий и завершением старой очереди перед переключением producer/worker на новые аргументы задач. Исторические завершённые задания не требуют выдуманных снимков; новые всегда содержат снимок. После переключения не оставлять автоматический fallback на `PARSER_FACTORIES`, скрывающий ошибки конфигурации.

`job_sites` не удалять попутно без проверки её фактического наличия и использования. Удаление старых Python-классов допустимо после переноса seed и обновления тестов, если runtime-ссылок на них больше нет.

1. Модели, схемы DTO, миграция и seed; начальные парсеры при регистрации.
2. `ParserRepository`, `ParserCatalogService`, Redis cache и CRUD с владением, версиями и транзакционным запретом удаления.
3. `ConfiguredVacancyParser`, параметризованная пагинация, построение URL и проверка результатов JS.
4. Снимки в автопарсинге, загрузка в Celery и асинхронная инициализация `VacancyScrapingService`; единый пользовательский путь разбора URL.
5. Страницы списка/создания/редактирования, Sidebar, query hooks, инвалидация и переводы.
6. Проверки поведения, миграции и сценария с двумя пользователями; переключение очереди.

## 12. Критерии приёмки и проверки

1. У существующего и нового пользователя есть собственные HH и GeekJob с JS из текущих реализаций. Изменение/удаление одним пользователем не влияет на другого; чужой ID даёт `404`.
2. Созданный сайт появляется сверху списка и участвует в следующем поиске без правки Python. После edit/save происходит возврат к обновлённому списку; дата создания не меняется.
3. Пагинация списка серверная; при одинаковом `created_at` порядок определяется `id DESC`. Удаление последнего элемента страницы корректирует страницу.
4. Тесты URL покрывают `text`/`qs`, константные и существующие параметры, кириллицу, пробелы, `&`, `?`, нечисловой ID и отсутствие двойного кодирования.
5. HH обходит страницы с `page=0`, GeekJob не вызывает JS пагинации; пользовательский сайт с `pagination_start=1` получает `1..N`. Проверить лимит, пустой результат и нечисловые номера.
6. Настройки каталога загружаются один раз на запуск, а не на каждую страницу/вакансию. Воркер использует сохранённый снимок даже после редактирования и повторной доставки сообщения.
7. Cache hit/miss, выключенный/недоступный Redis и запись старой ревизии после edit дают корректные настройки. Новый запуск после commit видит новую ревизию в другом API/worker-процессе.
8. Удаление занятого сайта возвращает `409` для `pending`, `running` и активного одиночного разбора. После завершения конкретного сайта удаление разрешено; история и вакансии остаются.
9. Конкурентные start/delete и edit/start проверить интеграционными тестами с двумя DB-сессиями. Ни одна задача не остаётся без снимка и нельзя удалить зарезервированный парсер.
10. Ошибка dispatch и ошибка/таймаут воркера освобождают занятость после прекращения работы. Ошибка одного парсера не мешает другим; генерация писем и события сохраняют существующее поведение.
11. Неверный JS/тип результата даёт диагностируемую ошибку сайта. Бесконечный JS ограничен deadline; пользовательский браузерный код не получает доступ к внутренним адресам и данным приложения.
12. Одиночный разбор URL использует личную конфигурацию; старый кеш текста другого пользователя или старой ревизии не подставляется.
13. Миграция и seed проверяются на существующих пользователях и истории; повторный seed не перезаписывает изменённые конфигурации.

Для реализации: добавить backend unit-тесты с fake repository/cache и HTML fixtures для извлечения, DB-тесты для блокировок и миграции. Backend-проверки выполнять по Docker-инструкциям проекта и запускать `make lint`. Frontend проверить сборкой `npm run build` и сценариями CRUD; при добавлении Vitest-тестов настроить test script. Успех текущих живых HH/GeekJob не использовать как единственный тест: внешний DOM может изменяться.
