# Генерация сопроводительных писем: ИИ или шаблоны

Статус: спецификация для реализации. Дата: 2026-09-19.

## 1. Задача и результат

В форме автоматического парсинга добавить переключатель способа генерации писем с вариантами «Использовать ИИ» и «Использовать шаблоны».

- В режиме ИИ сохранить текущую генерацию через настроенную LLM/Ollama.
- В режиме шаблонов собирать русскоязычное письмо программно по образцу `scripts/generate_cover_letter_dataset.py`, без вызовов LLM.
- Для шаблонов запускать генерацию автоматически сразу после успешного завершения парсинга, без второго нажатия. Для ИИ сохранить ручной запуск генерации.
- В обоих режимах получать проекты текущего пользователя через `ProjectRepository`, как в `backend/app/commands/generate_cover_letter.py`. Технологии брать из сохранённых проектов.
- `OPENINGS`, `CLOSINGS`, `PROJECT_LEADS`, `BRIDGES` разрешено хранить константами в backend.
- Сохранять результат в существующие поля вакансии и показывать через существующие карточки, модальное окно и механизмы прогресса.

Этот документ описывает будущую реализацию; создание спецификации само по себе не означает, что фича реализована.

## 2. Принятые продуктовые решения

Следующие решения уточняют неоднозначности исходного запроса и являются базовым вариантом реализации:

1. Переключатель находится в форме рядом с кнопкой «Парсить» и доступен до запуска. Дополнительное модальное подтверждение после нажатия не требуется.
2. Это один выбор из двух вариантов, а не два независимых boolean-флага. Одновременно активен ровно один режим.
3. По умолчанию выбран ИИ — это сохраняет поведение существующих клиентов и исторических заданий.
4. «Парсить» запускает сбор вакансий. Если выбраны шаблоны, backend сразу после успешного завершения всего задания парсинга автоматически запускает генерацию писем для найденных вакансий. Если выбран ИИ, генерация запускается отдельно кнопкой всей пачки либо кнопкой конкретной вакансии, как раньше. Для шаблонов второй клик не нужен. Генерация по мере сохранения отдельных вакансий до завершения парсинга в первую версию не входит.
5. Выбор сохраняется в задании парсинга и применяется ко всем его письмам, включая генерацию и повторную генерацию из карточки.
6. Для созданного задания режим неизменяем. Переключатель в форме задаёт режим следующего парсинга. В выбранном задании и панели генерации показывается его фактический режим.
7. Первая версия шаблонов пишет только по-русски, как исходный скрипт. Переключатель языка для такого письма скрыт или отключён с пояснением «Шаблонные письма доступны на русском языке».
8. Отдельные страницы генерации по произвольному тексту или URL сохраняют существующее поведение ИИ. Их собственный выбор режима не входит в задачу.

## 4. Интерфейс

### 4.1. Переключатель

Использовать один Chakra `Switch` с подписями двух состояний:

```text
[Поисковый запрос                         ] [Парсить]
Использовать шаблоны   [ переключатель ]   Использовать ИИ  [ⓘ]
```

- `checked = true` соответствует `ai`, `false` — `template`.
- В состоянии React хранить `GenerationMode`, а checked вычислять из него.
- Активную подпись визуально выделять; одного цвета для обозначения выбора недостаточно.
- Доступное имя switch: «Использовать ИИ». Tooltip доступен по hover и keyboard focus; на touch открывается нажатием на значок информации.
- Tooltip: «Если включить „Использовать ИИ“, генерация запускается отдельной кнопкой, а письмо создаёт нейросеть на основе вакансии и ваших проектов. В режиме „Использовать шаблоны“ письма создаются автоматически после завершения парсинга — из готовых фраз, ваших проектов и технологий, без обращения к нейросети».
- Во время отправки `/start` переключатель отключён вместе с остальной формой. Значение фиксируется в момент submit.
- Все новые пользовательские строки вынести в `i18n/locales/ru.json` и `en.json`.

### 4.2. Состояние задания

- Рядом с кнопкой генерации показать «Режим: ИИ» либо «Режим: Шаблоны».
- Для ИИ после завершения парсинга оставить кнопку запуска генерации. Для шаблонов показать автоматический переход «Парсинг завершён → Подготовка писем → Генерация → Письма готовы»; кнопку первичного запуска не показывать. Пока backend готовит автозапуск, не показывать пустое состояние с предложением запустить генерацию вручную.
- При ошибке автоматического запуска или генерации показать ошибку и кнопку «Повторить генерацию». После успешного завершения оставить просмотр писем и существующие действия повторной генерации.
- В истории заданий добавить компактную метку режима.
- После reload и выбора записи истории режим получать из API; localStorage с ID задания не является источником режима.
- Изменение формы нового поиска не меняет режим уже выбранного задания и не влияет на выполняющиеся задачи.
- После ошибки запроса запуска сохранять выбранное значение формы и показывать существующее сообщение об ошибке.
- Для карточки режим передавать от её задания; backend всё равно определяет его самостоятельно по БД.

## 5. Контракт данных и API

### 5.1. Общий тип и миграция

```python
class GenerationMode(str, Enum):
    AI = "ai"
    TEMPLATE = "template"
```

Разместить enum в общем модуле, например `backend/app/schemas/generation_mode.py`, без зависимости от API router или LLM. На frontend:

```typescript
export type GenerationMode = 'ai' | 'template';
```

В таблицу `parsing_jobs` добавить `generation_mode`: строковое поле `NOT NULL`, Python default и server default `ai`, CHECK на значения `ai`/`template`. Историческим строкам назначить `ai`. Использовать отдельную Alembic-миграцию `add_generation_mode_to_parsing_jobs.py` с актуальным `down_revision` на момент реализации.

Не добавлять два поля `use_ai`/`use_templates`. Отдельное поле в `AutoParsedJob` для этой версии не требуется: режим наследуется от неизменяемого задания. Вакансии без задания остаются в режиме ИИ.

### 5.2. Запуск парсинга

```http
POST /auto-parse/start
Content-Type: application/json

{"query": "Python Developer", "generation_mode": "template"}
```

- Поле необязательно для старых клиентов; отсутствие означает `ai`.
- `null`, неизвестное значение, boolean и пустая строка дают стандартный `422` до создания задания/публикации задач.
- Ответ сохраняет контракт `202 {"parsing_job_id": 123}`.
- `create_job_with_sites(..., generation_mode=GenerationMode.AI)` сохраняет значение в той же транзакции, что и job/site jobs.
- Сигнатуру `parse_site(job_id, site_key)` менять не нужно. Сам сбор вакансий одинаков для режимов; после финализации родительского задания orchestration-код читает сохранённый режим и при необходимости запускает генерацию по §5.6.

### 5.3. Чтение задания

`GET /auto-parse/status/{id}`, `GET /auto-parse/history` и parsing SSE `/auto-parse/stream/{id}` возвращают поле:

```json
{"generation_mode": "template"}
```

Это добавка к существующим полям, а не новый формат ответа. Обязательно обновить ручной `_serialize` SSE: он не получает новое поле автоматически из модели. SSE не должен затирать режим в React неполным объектом. Во временной совместимости со старым backend отсутствие поля читать как `ai`.

### 5.4. Генерация пачки

`POST /auto-parse/jobs/{id}/generate` сохраняет существующий запрос без body. Режим берётся только из задания, проверенного на принадлежность текущему пользователю.

```text
ParsingJob.generation_mode
  → start_batch(..., generation_mode=...)
  → single_generation(..., generation_mode="template")
  → GenerateLetterCommand(generation_mode=...)
  → handler.handle(...)
```

Новый аргумент Celery добавить в конец с default `ai`, передавать как keyword argument и сериализовать строкой. Это сохраняет исполнение старых сообщений с прежним набором аргументов. Перед постановкой новых сообщений обновить workers до версии, принимающей аргумент.

`GenerateLetterCommand.generation_mode` получает default `ai`. Для вакансии с заданием авторитетным остаётся сохранённый режим родителя: общий обработчик загружает его через репозиторий задания и проверяет/уточняет режим команды. Это защищает также одиночные вызовы и старые сообщения без поля. Если указан `parsing_job_id`, но родитель отсутствует, завершать ошибкой, а не молча выбирать ИИ.

Сохраняются проверки `404` для чужого/несуществующего задания и `400` для незавершённого парсинга. Повторный запуск во время активной генерации должен давать `409`; сейчас hook ожидает такой ответ, но route не реализует защиту. Проверку и фиксацию старта выполнить атомарно для задания, чтобы два запроса не поставили одну пачку дважды. Конкретный lock встроить в существующее состояние batch, с освобождением при завершении/ошибке запуска и ограниченным TTL на случай падения процесса.

Режим не меняет правила выбора вакансий для существующего batch: текущий endpoint передаёт все вакансии задания. Смена режима и отдельный механизм частичного перезапуска в эту задачу не входят.

### 5.5. Генерация из карточки

Добавить `POST /auto-parse/vacancies/{vacancy_id}/generate-stream` с существующим форматом потока писем: `data: {"delta": "..."}`, завершение `data: [DONE]`, ошибки `data: {"error": "..."}`.

- Авторизация — как у остальных запросов карточки. До начала потока проверить владельца вакансии и доступность родительского задания; чужая/несуществующая вакансия — `404`.
- Endpoint работает с существующим ID и не создаёт копию вакансии.
- Режим получает из `ParsingJob`, пользователь не передаёт override режима в body.
- Если для задания выполняется batch, вернуть `409`, чтобы одиночная генерация не перезаписывала письмо одновременно с пачкой. Повторный параллельный запрос для той же вакансии также не запускает вторую генерацию; согласовать блокировки одиночного и пакетного путей.
- Использовать тот же command handler и сохранение, что у пачки. Для шаблона текст можно отдать одним delta после сохранения, искусственная задержка не требуется.
- `VacancyModal` использует новый метод hook/client для кнопки и autoGenerate. Общий `streamFromText` остаётся для самостоятельной генерации по тексту.
- По завершении перечитать исходную вакансию/список либо обновить состояние родителя, чтобы письмо и `is_generated` были видны после закрытия окна. Простого обновления локального текста модального окна недостаточно.
- При повторной генерации шаблона одинаковые входные данные могут дать тот же текст; обещания нового случайного варианта в UI не требуется.
- Для шаблонов первичная генерация принадлежит автоматическому batch: до его окончания не запускать `autoGenerate` модального окна и отключить ручной запуск, включая промежуток между завершением парсинга и постановкой batch. Для ИИ оставить прежнюю возможность ручной генерации. После завершения шаблонного batch разрешить повторную генерацию и повтор ошибочного письма.

### 5.6. Автоматический запуск шаблонов

Автозапуск выполняется на backend. Frontend не должен вызывать `/generate` из `useEffect` при получении `status=done`: закрытая вкладка, reload, две вкладки или повтор SSE не должны влиять на запуск.

```text
Нажатие «Парсить»
  → создание job с generation_mode
  → выполнение всех parse_site
  → финализация родительской job и commit
      ai       → ожидание ручного запуска
      template → автоматический start_batch с generation_mode="template"
                  → single_generation → сохранение писем → события прогресса
```

Правила:

1. Запускать только после перехода родительского задания в `done`, когда все сайты завершены и вакансии закоммичены. Завершения одного сайта недостаточно.
2. После `finish_site` вызвать общий сервис `maybe_start_template_generation(job_id)`, например из orchestration-слоя `parse_site` после `SiteParseService.run`. Сервис перечитывает job и проверяет режим/статус. При одновременном завершении сайтов повторные вызовы допустимы, повторный batch — нет.
3. Автоматический и ручной запуск используют общий механизм из §5.4, одинаковые проверки конкуренции и один генератор. Не вызывать HTTP endpoint из Celery и не дублировать подбор проектов/сборку писем внутри парсера.
4. Факт автоматического запуска фиксировать устойчиво в БД: добавить nullable `auto_generation_started_at` в `ParsingJob`, default `NULL`, для старых строк также `NULL`. Claim на автозапуск выполнять атомарно под блокировкой job; повтор финализации после завершённой генерации не должен запустить письма заново. Это поле относится к автозапуску и не запрещает явную повторную генерацию пользователем.
5. Отдельно хранить nullable `auto_generation_error`, default `NULL`, для ошибки постановки batch. При ошибке не помечать генерацию успешной, не переводить успешный парсинг обратно в `failed`; отображать ошибку генерации и разрешать явный повтор. Маркер claim сам по себе не доказывает успешную публикацию задач: обработать сбой между claim и enqueue, частичную публикацию и восстановление после падения процесса. При реализации выбрать устойчивую запись намерения с повторной доставкой либо сверку незавершённого запуска; задачи должны быть защищены от повторного выполнения одной автоматической попытки. Одной проверки Redis-lock с TTL для этого недостаточно.
6. Если вакансий нет, не создавать пустой batch и не ждать события генерации. Показать «Вакансии не найдены»; состояние автогенерации — `skipped`.
7. Если итоговый парсинг `failed`, автоматическую генерацию не запускать, включая случай частично сохранённых вакансий. Показать ошибку парсинга; расширение генерации на частичные результаты не входит в эту версию.
8. Ошибка отдельного письма не отменяет генерацию остальных. Повтор после ошибки не должен конкурировать с уже поставленными задачами; сначала завершить/согласовать текущую попытку.
9. Для `ai` никакой автоматический batch не ставится. Новые поля не запускают генерацию исторических заданий при чтении history/status или миграции.

Расширить `GET /auto-parse/jobs/{id}/generate-status` полем `auto_generation_status`: `not_applicable | waiting_for_parse | pending | started | failed | skipped`, а также nullable `auto_generation_error`. Это статус автоматического запуска, а не итог каждого письма: после успешного dispatch он остаётся `started`, завершение определяется существующими счётчиками и статусами задач. `failed` здесь означает сбой запуска; ошибки писем остаются в существующем generation status. Для ИИ возвращать `not_applicable`; для шаблонов до завершения парсинга — `waiting_for_parse`, после `done` до dispatch — `pending`, при пустом результате или неуспешном парсинге — `skipped`.

Клиент при переходе шаблонной job в `done` сам подключается к наблюдению генерации и делает HTTP-сверку, не отправляя команду запуска. Пока статус `pending`, продолжает polling; после `started` использует обычное восстановление прогресса. При reload/history действует тот же алгоритм.

## 6. Backend: разделение подбора данных и генератора

### 6.1. Общий контекст

Выделить подготовку контекста в метод обработчика или небольшой сервис, общий для обоих режимов:

1. Загрузить вакансию через `AutoParseJobRepository.get_by_id`.
2. Определить владельца и режим родительского задания; не брать user ID из произвольного тела запроса.
3. Вызвать `get_projects_by_vacancy_text(f"{job_title}\n{job_text}", vacancy.user_id)`.
4. Если ответ пустой, вызвать `get_by_user(vacancy.user_id)`.
5. Использовать `project.name` и `project.technologies`. `RelevantProjectResponse.project_name` сейчас заполнен из `company_name`, поэтому его нельзя подставлять вместо названия проекта.
6. Передать контекст выбранному генератору и сохранить непустое письмо через `update_vacancy(vacancy.id, text, is_generated=True)`.

Для ИИ сохранить текущие prompt, модель, поля запроса, имена пользователя, список проектов и получение технологий. Ограничение до трёх проектов ниже применяется только к шаблонам.

### 6.2. Изоляция от LLM

Новый модуль `backend/app/services/template_cover_letter.py` содержит константы и чистую сборку текста. Он не импортирует Ollama, prompts, LangChain и исполняемый скрипт из `scripts/`, не читает CSV/JSON и не обращается к сети.

`build_handler` сейчас безусловно создаёт `CoverLetterPrompt`, `JobParsePrompt`, `RelevantProjectsPrompt`. Перевести создание LLM-зависимостей на ленивые фабрики/ветку `ai`, чтобы для шаблонов не требовались доступность Ollama и инициализация клиентов. Новый endpoint карточки не должен ради шаблона создавать `CoverLetterService`, чей конструктор также безусловно создаёт prompts; использовать общий handler напрямую либо сделать зависимости сервиса ленивыми.

В шаблонной ветке запрещены вызовы генерации, embeddings, LLM-извлечения требований и LLM-ранжирования. PostgreSQL, Redis и Celery остаются обычными зависимостями приложения. Ошибка шаблона не вызывает автоматический fallback к ИИ; ошибка ИИ не переключает режим самопроизвольно.

## 7. Алгоритм шаблонного письма

### 7.1. Проекты и технологии

1. Источник проектов — только общий repository pipeline из §6. Не переносить `read_csv` и `select_projects` из скрипта: ранжирование уже сделано репозиторием.
2. Сохранить порядок релевантности. При равном SQL score добавить стабильный tie-break по `Project.id`; fallback `get_by_user` уже упорядочен по ID.
3. Удалить дубли проектов по ID, пропустить проекты с пустым после trim названием, взять первые три пригодных проекта.
4. Для каждого проекта использовать только его сохранённые `technologies`: trim, удалить пустые строки, убрать повторы без учёта регистра с сохранением первого написания и порядка. Поле уже является массивом — CSV-парсер с удалением `{}` здесь не нужен.
5. Строка проекта: `«Название» — Python, FastAPI`. При отсутствии технологий: `«Название»`, без висячего тире.
6. Технологии в общей строке стека брать только из включённых в письмо проектов. Нельзя добавлять технологию из вакансии, отсутствующую в этих проектах.

### 7.2. Подбор фраз и структура

- Взять начальные наборы `OPENINGS`, `CLOSINGS`, `PROJECT_LEADS`, `BRIDGES` из скрипта и разместить в новом backend-модуле; редактор шаблонов и таблица в БД не нужны.
- Базовый вариант определяется стабильно: `variant = vacancy_id`, где ID — внутренний `AutoParsedJob.id`, не внешний ID сайта.
- Каждый набор индексировать отдельно: `variant % len(OPENINGS)`, `variant % len(BRIDGES)` и т. д. Все наборы должны быть непустыми.
- Стиль блока проектов — `variant % 8`. Восемь вариантов компоновки можно адаптировать из `make_letter`, но фразы про «другие проекты» выводятся только при наличии второго проекта.
- Получается одно письмо на вакансию. Циклы по вариантам для SFT-датасета и экспорт instruction/input/output не переносятся.
- Для одинакового ID и одинакового контекста результат одинаковый; изменение сохранённых проектов может менять текст при повторной генерации. Снимок портфолио на момент парсинга не вводится.

Порядок блоков:

```text
Приветствие и название вакансии

Связующая фраза

Вводная фраза к проектам, если непустая

От одного до трёх проектов с технологиями

Строка совпавшего стека либо нейтральная фраза

Завершение
```

Блоки соединяются `\n\n`; пустые пропускаются. Возвращается готовый plain text, без JSON, Markdown-заголовков и служебных комментариев. Не добавлять достижения, стаж, метрики, компании или навыки, которых нет в исходных данных. ФИО и подпись не обязательны: их нет в шаблоне скрипта.

### 7.3. Совпадение технологий

Сохранить идею `matching_technologies`: сравнить название и текст вакансии с технологиями выбранных проектов, убрать дубли и взять максимум четыре совпадения для строки `Стек: …`.

Производственный matcher должен быть отдельной чистой функцией и учитывать технические имена:

- сравнение без учёта регистра;
- границы слов/названий вместо произвольного substring: `Java` не совпадает с `JavaScript`;
- символы внутри `C++`, `C#`, `.NET`, `Node.js`, `CI/CD` значимы;
- для многословного названия допускается нормализация повторных пробелов;
- не вводить неявные синонимы вроде `JS → JavaScript` в первой версии;
- не переносить `STOP_WORDS` скрипта без изменений: он исключает SQL, JavaScript, HTML/CSS и может скрывать реальные совпадения.

Если совпадений нет, использовать нейтральную фразу из скрипта: «Проекты помогают предметно обсудить, какие задачи и технологии могут быть релевантны позиции». Не утверждать точное совпадение опыта: для `BRIDGES` в этом случае выбирать нейтральный поднабор, например «Ниже приведу проекты, которые могут быть полезны в контексте этой роли»; для `PROJECT_LEADS` — «В портфолио представлены следующие проекты:». Все такие поднаборы также индексировать по собственной длине.

### 7.4. Пустые и неполные данные

| Случай | Поведение |
| --- | --- |
| Один проект | Упоминание только этого проекта, без пустой фразы «Также…» |
| Два проекта | Использовать оба, не ожидать третий |
| Больше трёх | Первые три пригодных после repository selection |
| Нет проектов либо все имена пустые | Приветствие и завершение; без блока портфолио, стека и утверждений об опыте |
| У проекта нет технологий | Оставить название; не придумывать стек |
| Нет совпадений с вакансией | Реальные проекты и нейтральные фразы из §7.3 |
| Пустое название вакансии | «Здравствуйте! Хочу откликнуться на вашу вакансию.» |
| Пустой текст вакансии | Искать совпадения по названию; дальше обычный fallback |
| Вакансия не найдена | `not_found` в task, `404` в одиночном HTTP-вызове; не успешное пустое письмо |
| Ошибка БД/сборки/сохранения | `failed`; не публиковать успешное событие и не переключаться на ИИ |

У текущего скрипта `BRIDGES` содержит семь элементов при восьми стилях; индексировать все списки через общий `style` небезопасно. `descriptions[0]` и `variant % len(ranked)` также требуют непустых списков. В backend эти ошибки переносить нельзя. Изменять сам dataset-скрипт для реализации фичи не требуется.

### 7.5. Иллюстрация результата

Для вакансии «Python Backend Developer» с Python/FastAPI в описании и сохранённого проекта «Сервис вакансий» с технологиями Python/FastAPI/PostgreSQL допустим такой текст:

```text
Добрый день! Заинтересовала вакансия Python Backend Developer.

Ниже приведу проекты, которые могут быть полезны в контексте этой роли.

В портфолио представлены следующие проекты:

«Сервис вакансий» — Python, FastAPI, PostgreSQL.

Стек: Python, FastAPI.

Буду рад подробнее обсудить задачи команды и свой релевантный опыт.
```

Пример иллюстрирует состав письма, а не фиксирует фразы для конкретного `vacancy_id`.

## 8. Сохранение, ошибки и обновление интерфейса

- Успешные режимы используют одинаковые `cover_letter_text` и `is_generated=True`.
- Успешное Redis/WS-событие публикуется только после сохранения письма. Формат `batch_id`, `vacancy_id`, `status`, `cover_letter_text` сохраняется; допускается дополнительное `generation_mode`.
- Сейчас `handle` ловит исключение и фактически возвращает `None`, а Celery затем ставит `generated`. Исправить это в общем пути: логировать и пробрасывать исключение; пустой/нестроковый результат не считать успехом.
- При ошибке повторной генерации ранее сохранённое письмо не очищать. Статус попытки и наличие старого письма — разные состояния.
- Полный передел транспорта прогресса не требуется, но работоспособность обоих режимов нужно проверить с фактическим контрактом: backend generation SSE отдаёт named `snapshot`, отдельные статусы вакансий и named `complete`; frontend сейчас ожидает агрегированный объект в `onmessage`.
- В рамках интеграции обновить клиент: слушать `snapshot`/`complete`, хранить последнее состояние по vacancy ID, обрабатывать `started`/`generated`/`failed`/`not_found`, а на завершении/восстановлении сверяться с `generate-status` и перечитывать вакансии.
- Терминальные состояния считать по уникальным vacancy ID. Повтор одного события не увеличивает счётчик. При смешанном результате показать число ошибок и завершить индикатор; `done` означает отсутствие ошибок в закончившейся попытке, `failed` — наличие ошибок.
- Быстрый шаблонный batch может завершиться до открытия SSE. Начальный snapshot и HTTP-сверка должны восстановить результат; при полностью терминальном snapshot сервер сразу отправляет `complete`.
- Автозапуск и парсинг имеют отдельные состояния: `ParsingJob.status=done` сообщает только об окончании сбора вакансий. Шаблонная генерация после него может ожидать постановки, выполняться или завершиться ошибкой. UI наблюдает её автоматически по §5.6.
- Результат HTTP/SSE старого задания не должен менять активное задание после переключения истории. Закрывать старую подписку и проверять актуальный ID при обработке асинхронных ответов.
- При разрыве generation SSE выполнить HTTP-сверку; если попытка активна — восстановить подписку или продолжить polling до терминального состояния. Однократного закрытия потока недостаточно.

## 10. Проверки

### Unit и API

Предлагаемые backend-файлы: `tests/test_template_cover_letter.py`, `test_generate_cover_letter.py`, `test_generation_mode_api.py`, `test_single_generation.py`. Дополнить существующие repository-тесты там, где меняется сигнатура.

Обязательные проверки:

1. Default `ai`, явные `ai`/`template`, отклонение неизвестных значений; сохранение и возврат через status/history/SSE.
2. Обе ветки вызывают repository selection с владельцем вакансии и fallback только при пустом результате.
3. AI-ветка вызывает прежний prompt с прежними данными; шаблонная ветка не вызывает ни один prompt/LLM factory. Использовать заглушки, падающие при попытке создания или вызова LLM.
4. Шаблон содержит только переданные проекты/технологии; максимум три проекта и четыре совпадения в общей строке стека; порядок стабилен.
5. Ноль проектов, один проект, пустые технологии/название вакансии, дубли, отсутствие совпадений и все восемь стилей дают корректный текст без пустых конструкций.
6. Matcher: разные регистры, SQL, JavaScript, C++, C#, .NET, Node.js, многословные имена; Java не совпадает с JavaScript.
7. Исключение сборки или сохранения не публикует `generated`; неизвестный ID даёт `not_found`/`404`.
8. Новые задачи получают выбранный режим, старые аргументы остаются валидными; существующая template-job определяет режим даже для команды без нового поля.
9. Одиночная генерация изменяет исходную вакансию и не создаёт новую; чужая вакансия не генерируется.
10. Параллельные запросы генерации не создают конкурирующие запуски; fast batch, snapshot, дубли terminal events и mixed failure завершают прогресс правильно.
11. После завершения всех сайтов template-job автоматически ставит batch; ai-job не ставит. Завершение первого сайта, пустая выдача и итоговый `failed` не запускают генерацию.
12. Одновременная финализация сайтов, повтор task и повторная проверка уже завершённого задания не создают второй автоматический batch; закрытая вкладка не препятствует автозапуску.
13. Сбой между claim и enqueue, частичная публикация и повтор после сбоя не дают ложного успеха и не создают конкурирующих генераций; состояние восстанавливается по §5.6.

Frontend: switch, submit payload, сохранённый режим против режима формы, reload/history, tooltip с клавиатуры, путь карточки по ID, завершение до SSE-подписки, HTTP-восстановление и поздний ответ предыдущего задания. Дополнительно: template-job начинает наблюдение без POST `/generate`, ai-job ждёт кнопку, `pending` не выглядит как ручной idle, модальное окно не запускает конкурентную первичную генерацию шаблонов. В текущем `frontend/package.json` уже есть `npm run test` (`vitest run --passWithNoTests`); добавлять второй script не нужно. Проверить фактический запуск добавленных тестов, поскольку успешный exit при отсутствии тестов ничего не подтверждает.

### Ручной сценарий

1. Открыть автопарсинг: включён ИИ, tooltip объясняет оба режима.
2. Выбрать шаблоны и нажать только «Парсить»: после завершения сбора вакансий генерация начинается сама, второго клика нет.
3. Во время парсинга закрыть вкладку, затем открыть историю: генерация запустилась на backend, сохранён режим шаблонов.
4. Открыть автоматически созданное письмо: использованы проекты пользователя, исходная запись обновлена, LLM не вызвана.
5. Проверить быстрый batch и перезагрузку в промежутке между parsing `done` и dispatch: письма и прогресс восстанавливаются, лишний batch не создаётся.
6. Повторить генерацию из карточки после batch: режим остаётся шаблонным; при ошибке автозапуска доступна явная кнопка повтора.
7. Создать новое задание в режиме ИИ: после парсинга генерация сама не начинается; нажатие прежней кнопки запускает путь через настроенную модель.
8. Открыть старое задание до миграции: отображается ИИ.
9. Проверить пользователя без проектов: шаблонное письмо корректно, выдуманного портфолио нет.
10. Проверить narrow viewport, Tab/Space и tooltip; изменение формы нового поиска не меняет режим старого задания.

Backend-проверки запускать внутри `app-backend` из `/app`, согласно Docker-процессу проекта:

```sh
docker exec app-backend sh -lc 'cd /app && uv run python -m unittest discover -s tests'
docker exec app-backend sh -lc 'cd /app && make lint'
```

Frontend — из `frontend/`:

```sh
npm run test
npm run build
```

Миграцию проверять на отдельной тестовой БД. Реальные LLM-вызовы не нужны для unit-тестов. В отчёте реализации отдельно указать выполненные проверки и существовавшие ранее сбои; не считать непроверенные сценарии успешными.

## 11. Критерии готовности

- [ ] До запуска парсинга пользователь видит оба режима и понятный tooltip.
- [ ] Старые запросы и задания используют ИИ; текущий AI-путь сохранён.
- [ ] Выбранный режим хранится на backend, переживает reload и историю, доходит до Celery.
- [ ] Для шаблонов после успешного непустого парсинга генерация начинается автоматически на backend без второго клика; для ИИ остаётся ручной запуск.
- [ ] Закрытая вкладка не мешает автозапуску; параллельная финализация сайтов не создаёт дубли, пустой/неуспешный парсинг не запускает batch.
- [ ] Шаблонные письма получают проекты и технологии из репозитория пользователя, без CSV и без LLM на любом этапе.
- [ ] В шаблонах используются заданные группы фраз, корректно обработаны пустые данные и все стили.
- [ ] Пакетная генерация и кнопка карточки соблюдают один и тот же режим задания.
- [ ] Успех публикуется после сохранения; ошибки не превращаются в успешные пустые письма.
- [ ] Быстрая генерация и повторное подключение корректно отображаются в UI.
- [ ] Миграция, целевые тесты, lint и build проверены; ограничения отражены в PR.

## 12. За пределами задачи

Не включать в эту реализацию редактор шаблонов, пользовательские наборы фраз, дополнительные языки шаблонов, обучение/смену модели Ollama, экспорт SFT-датасета, изменение сайта-парсера, embeddings для подбора проектов, смену режима уже созданной job и автоматическую отправку откликов работодателю.
